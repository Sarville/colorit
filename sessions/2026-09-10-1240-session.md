# Session 2026-09-10 (1240) - Score system, reset progress, daily levels (pool + generator + solver)

## Summary
Three big features, delivered iteratively with a lot of course-correction from live feedback:

1. **Score system** - points formula for the 3 normal packs (group-of-5 progression, bonus for
   optimal-move clears, penalty for slow ones), shown on the main menu. Went through several
   visual iterations (brush-stroke heading → bigger brush + white outlined text → final: a glossy
   "achievement medal" badge built from the same primitives buttons/tiles already use, since a
   stretched heading-brush image was never really the right material for a two-line label+number
   stack).
2. **Reset progress** - Settings entry + confirm modal. Found and fixed the actual bug behind
   "progress doesn't save in dev": `cloudSave.ts` was treating Yandex's offline "lite" SDK
   fallback (which resolves non-null even with zero real Yandex parent frame) as a real player,
   so every save/load went through a fake object instead of falling through to localStorage.
3. **Daily levels** - by far the largest piece, rebuilt from scratch three times based on user
   review at each stage:
   - v1: reused existing pack levels - rejected implicitly (superseded before real review).
   - v2: recolor a real level's exact layout (color permutation = graph isomorphism, proven via a
     BFS solver on 6 real levels spanning every modifier type) - user's verdict: "это просто
     перекраска" (just recoloring), wanted *real* generation.
   - v3: real procedural generation (random modifiers/walls-free layout, generate-and-test via the
     solver) - worked, but the user then asked for a proper pre-built 300-level pool with
     accumulating daily history instead of per-user live generation, which is what shipped:
     - `lib/levelSolver.ts`: BFS solver over reachable board states (not move sequences), with
       optional `maxStates`/`maxTimeMs` budgets.
     - `lib/proceduralGenerator.ts`: generate-and-test candidate builder (no forced walls between
       regions, unlike the very first strip-based attempt the user rejected as "not a puzzle").
     - `levels/build-daily-pool.ts`: assembles the pool from two sources - Community pack levels
       with a hand-recorded solution (trusted as-is, not re-solved - re-verifying a 20+ move
       puzzle from scratch can take 30s-3min+ and isn't always possible even then), topped up by
       generated levels. Difficulty tiers are by measured move count (Easy/Medium/Hard), not
       which source they came from.
     - `lib/dailyLevels.ts`: rewritten for an **accumulating history** (`DailyHistoryData.days`),
       not a single replaced-daily entry - each new local day appends a fresh 5-level draw (1
       Easy + 1 Medium + 1 Hard + 2 random from the pool) instead of overwriting; past days stay
       visible and playable forever. Scoring for a slot is computed and *locked in* at the moment
       it's completed (`recordDailyBest`), using whether that slot's day was still "today" *right
       then* - so completing an expired day's level later always pays the flat per-difficulty
       rate with no perfect-clear bonus, and an on-time clear's bonus is never retroactively lost
       just because the calendar moved on.
     - Tiles are sorted easiest-first within each day (by `optimal`) for display/navigation, using
       each tile's own carried `(date, slotIndex)` rather than array position, so sorting never
       touches which slot a completion is recorded against.
   - Two real bugs found via live testing and fixed:
     - `dailyPlayIndex` (né `dailySlot`) wasn't cleared when opening a normal-pack level, so once
       you'd ever visited Daily, every normal level looked frozen on whatever daily tile was last
       selected - `LevelPicker.tsx` now clears it explicitly on a non-daily tile open.
     - Rebuilding `levels/DailyPool.ts` reorders/replaces entries, so a `poolIndex` a client saved
       before a rebuild can end up pointing at a different (or out-of-range) level afterward -
       this is exactly what broke the user's daily level 5 mid-session. Fixed with a
       `DAILY_POOL_VERSION` stamp (`levels/DailyPool.ts`); `ensureTodayEntry()` redraws *today's*
       picks fresh when the stored version doesn't match (safe - today is the only day that can
       still be un-started), and `flattenDailyHistory()` skips (doesn't crash on) an out-of-range
       slot in an already-past day instead.
   - Final pool rebuild (per explicit user instructions): generated levels below 5 moves discarded
     as "too simple"; **all** Community levels with a recorded solution kept regardless of move
     count (they're already human-verified); Hard-tier generation given a much larger per-candidate
     solver budget (up to 120s) to see if it could find more long solutions - final composition:
     **203 levels: 100 Easy, 67 Medium, 36 Hard** (both Medium and Hard fell short of the 100/tier
     target - Easy/Medium generation is fast and reliable, but random-candidate generation almost
     never produces a genuinely long (12+ move) solvable puzzle even with a big time budget, since
     BFS just finds a short way out first when one exists; Hard leans mostly on the 24 Community
     levels that happen to classify that way, +12 generated).
