# Colorit - project notes for Claude

## Deployment (manual, no CI)
- VK build: `NEXT_PUBLIC_REQUIRE_VK=true yarn next build && yarn next export`, then
  `rsync -az --delete out/ server-games:/opt/games/site/vk/colorit/` (`server-games` is an SSH
  alias).
- Yandex build: `NEXT_PUBLIC_YANDEX_HOSTED=true yarn next build && yarn next export`, then zip
  the **contents** of `out/` (not the `out/` folder itself - `index.html` must sit at the zip
  root) into `colorit-yandex.zip`, uploaded by hand via the Yandex Games cabinet.
  - **Gotcha, hit more than once:** `next export` writes the 404 page twice -
    `out/404.html` *and* `out/404/index.html`. The Yandex cabinet's uploader scans the whole
    archive for `index.html` and rejects it ("Не найдено ни одного, либо найдено несколько
    файлов index.html") if it finds more than one. Exclude the `out/404/` subfolder when
    building the zip - keep the top-level `404.html`, drop `404/index.html`.
- Server runs Caddy (`caddy-games` container, config at `/opt/games/Caddyfile` on the host) and a
  small Node service `vk-payments-colorit` (payments webhook + VK launch-auth gate, code at
  `/opt/games/vk-payments/server.js` on the host). Both are tracked in this repo under
  [`ops/`](./ops/) - see [`ops/README.md`](./ops/README.md) for the deploy steps; a `git commit`
  alone does **not** update the live server. `vk-payments-colorit` needs
  `docker restart vk-payments-colorit` after any edit (no hot-reload); Caddy needs
  `docker exec caddy-games caddy reload --config /etc/caddy/Caddyfile` after validating with
  `caddy validate`.
- Before touching anything VK-related (payments, auth, storage, Caddy config), read
  [`docs/vk-gotchas.md`](./docs/vk-gotchas.md) - it documents several non-obvious traps that already
  cost real debugging time: `@vkontakte/vk-bridge`'s types being wrong for the order box response,
  VK's storage 4096-byte-per-key silent truncation, Caddy's `path` matcher not supporting `**`
  across segments in the deployed version, and how the VK launch-params auth gate works.

## OK (Odnoklassniki) payments (added 2026-09-15)
- OK runs the same VK Mini App with no client-side changes (same `vk_user_id`/`sign` launch params
  plus an extra `vk_client=ok`, same `VKWebAppShowOrderBox` call) - only the payments webhook needed
  new code. `get_item` for OK still arrives on the existing classic VK POST channel (branches on the
  `site` param for currency); OK's purchase *confirmation* is a separate GET route,
  `/vk/colorit-payments/ok`, signed with the **same** `VK_APP_SECRET` (confirmed on the live
  server - OK has no secret of its own here, don't assume otherwise). Must be set as "URL для
  платёжных уведомлений Одноклассников" in the dev.vk.ru cabinet.
- `ITEM_PRICE`/`ITEM_PRICE_OK` (`ops/vk-payments/server.js`) and `VK_ITEM_PRICE`/`OK_ITEM_PRICE`
  (`lib/support.ts`) must be kept in sync - the former is what's actually charged, the latter is
  only the button label. Neither VK votes nor OK OKi convert 1:1 to RUB or to each other, and
  there's no API to look up the rate - only each platform's own purchase-pack UI shows it. See
  `docs/vk-gotchas.md`'s "OK (Odnoklassniki) payments" section for the full writeup, including what
  still needs verifying against a real OK notification.

## Android / RuStore build (added 2026-09-24)
- Third target: Capacitor wraps the static export (`npm run build:android`, flag
  `NEXT_PUBLIC_ANDROID=true`, `lib/android.ts`) into an offline APK/AAB in `android/`. Ads = Yandex
  Mobile Ads via `@quenary/capacitor-yandex-ads`; purchases = RuStore Pay SDK 10.5.0 through our own
  `RuStorePayPlugin.java` / `lib/rustorePay.ts`. Two products: `support_author` (NON_CONSUMABLE,
  ad-free, restored from `getPurchases`) and `support_more` (CONSUMABLE donation once ads are off).
- Gradle needs **JDK 21** (JDK 25 breaks Gradle 8.14). Full build/release checklist and the list
  of things that still need the RuStore/РСЯ cabinets: [`docs/android-rustore.md`](./docs/android-rustore.md).
- rustore.ru/help sits behind an anti-bot 429 page for scripted fetches; SDK API was read straight
  from the AAR on RuStore's Maven (`artifactory-external.vkpartner.ru/artifactory/maven`).

## UI redesign conventions ("Kolorit" paint-splash look, since commit `498bc1c`)
- Shared primitives live in `styles/global.css` (`.col-panel`, `.col-circle`, `--col-blue-gloss`)
  and `components/FlagButton.tsx` (the pointed/rounded flag-shaped button used for every primary
  action) - reuse these instead of one-off button/panel CSS on a new screen.
- Section headings use a common pattern: a `brush_paint.webp` image absolutely centered behind
  the heading text (see `LevelPicker`/`SelectPack`/`Settings`/`Tutorial`/`Game` for the
  `*Wrap`/`*Bg`/heading three-part structure) - copy that pattern for any new heading rather than
  the plain `col-heading` pill (still used for a couple of inline/compact labels only).
- Real devices (especially portrait phones and landscape/short viewports) have repeatedly
  surfaced bugs invisible at a single desktop viewport width: background/decoration cropping,
  header-vs-board width mismatches, tap-highlight artifacts. Test at multiple widths (mobile
  portrait ~360-430px, landscape ~similar heights, tablet/desktop 900px+) before calling a visual
  change done.
- No Playwright/puppeteer dependency in this project - visual verification during past sessions
  installed `playwright-core` or `puppeteer-core` ad hoc into a scratch dir (driving the system
  `google-chrome` via `executablePath`) rather than adding it to `package.json`. Reasonable to
  repeat for one-off screenshot verification; not meant to become a real test suite without a
  deliberate decision.
- Post-purchase "thank-you" animation (`lib/support.ts`'s `shouldShowThankYouAnimation` /
  `isOnKnownPlatform`, rendered in `MainMenu`): gated so it's never fetched without a confirmed
  purchase, except when neither a VK nor a real Yandex launch is detected (local/standalone dev),
  where it always shows. See `docs/vk-gotchas.md`'s "Yandex SDK vs VK environment" section for why
  that check reads `ysdk.environment.app.id` rather than just `getYsdk() !== null`.
- `brush_paint.webp` (the heading-brush image) is shaped for **one line** of heading text behind
  it - stretching it to cover a two-line label+number block (tried for the main menu score) looks
  wrong at any size. For that kind of "number in a badge" UI, build a small glossy badge from
  `--col-blue-gloss` + a `col-heading`-style pill instead (see `MainMenu.module.css`'s
  `.scoreMedal`/`.scoreLabel` for the pattern) - it matches the button/tile material already used
  everywhere else in the app.

## Puzzle engine, solver, and daily-level pool (added 2026-09-10)
- `lib/gameEngine.ts` is the single source of truth for the click mechanics (`loadLevel`,
  `updateGame`, `checkGameIsWon`) - `components/Game/Game.tsx` (the live board) and
  `lib/levelSolver.ts`/`lib/proceduralGenerator.ts` (offline tooling) both import from it. Never
  reimplement the mechanics a second time for a tool/script - always import this.
- `lib/levelSolver.ts`'s `solveLevel()` is a plain BFS over reachable board states (not move
  sequences), so the first win it finds is provably the minimum-move solution. It's genuinely
  correct (verified against 6 real hand-authored levels spanning every modifier type - arrows,
  bombs, rotating arrows, circles, pre-filled cells) but has real limits: a puzzle with a true
  20+ move solution can take 30s-3+ minutes to verify from scratch, or fail to finish at all
  within a generous budget (`maxStates`/`maxTimeMs`) - don't assume "solver says unsolvable" means
  the board is broken without also considering it just ran out of budget on a genuinely hard one.
- `levels/DailyPool.ts` is **generated** by `levels/build-daily-pool.ts` - don't hand-edit it.
  Re-running that script produces a differently-ordered/differently-sized pool every time (random
  generation), which is why it carries a `DAILY_POOL_VERSION` stamp that `lib/dailyLevels.ts`
  checks against a client's saved data - if you ever restructure how the pool is built, make sure
  a fresh version stamp still gets written, or old clients' saved `poolIndex` values will silently
  point at the wrong (or out-of-range) levels.
- Dev scripts under `levels/*.ts` (`build-daily-pool.ts`, `generate-daily-sample.ts`,
  `test-solver-on-real-levels.ts`, etc.) need two extra ts-node flags beyond the plain
  `convert-levels.ts` invocation, because they pull in `levels/DailyPool.ts` /
  `components/Square/squareTypes.ts`-adjacent code: `-r ./levels/cssStub.js` (stubs `.css`
  imports so a transitive `.module.css` require doesn't crash plain ts-node) and
  `-r tsconfig-paths/register` (resolves the `@/...` alias) plus `-O '{"jsx":"react"}'` if the
  import chain reaches an actual `.tsx` file. Copy the exact command from the top-of-file comment
  in whichever script you're running rather than guessing the flags.
- **Testing a real puzzle live** (verifying a generated/pool level is actually solvable in the
  browser, not just "looks right"): don't hand-click boards or spam every modifier - use
  `lib/levelSolver.ts` to get the real minimal path, then replay those exact `{x,y}` coordinates
  via Puppeteer against `[class*="gameBoard"] [class*="row"]` buttons. Pattern used throughout
  this session: dump a live daily set's `poolIndices` from `localStorage`, resolve each to a
  `DailyPool` entry in a small ts-node script, solve each with `solveLevel()`, save the paths to a
  JSON file, then feed those into the Puppeteer script that seeds `localStorage` and clicks the
  real path. This caught a real decoder bug (a modifier-grid character can also mean "this
  non-modifier cell starts pre-filled with this color" - missed on the first pass) that pure
  visual/manual review wouldn't have.
- `lib/cloudSave.ts` must use `getRealYsdk()` (from `lib/yandexSdk.ts`), never plain `getYsdk()` -
  the plain one resolves to a non-null "lite" SDK even with zero real Yandex parent frame (see the
  `docs/vk-gotchas.md` entry this links to), so using it here silently breaks saving in local dev
  (every save appeared to succeed but went into a fake in-memory player, not localStorage). This
  was an actual shipped bug this session, root-caused and fixed - watch for the same mistake if
  `cloudSave.ts` or its callers are touched again.
